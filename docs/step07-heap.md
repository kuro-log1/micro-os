# Step 07 — 커널 힙 (kmalloc / kfree)

지금 커널은 4KB 프레임 단위로만 메모리를 얻을 수 있습니다. 하지만 커널이 실제로 만들 객체들은 대부분 작습니다. 프로세스 정보 구조체는 수십~수백 바이트, 파일 이름은 수십 바이트, 디렉터리 노드도 그 정도입니다. 이런 것 하나에 4KB를 통째로 주면 메모리의 90% 이상이 낭비됩니다.
C 프로그램에서 `malloc` 이 하는 일, 즉 큰 메모리를 미리 얻어 두고 요청이 올 때마다 필요한 크기만큼 잘라 주는 일을 커널 안에서도 해야 합니다. 이번 단계에서 만드는 것이 그 커널판 `malloc`, **`kmalloc` / `kfree`** 입니다.
이 단계로 커널 메모리 관리의 3층 구조가 완성됩니다. 맨 아래 PMM(Step 05)이 물리 프레임을 주고, 그 위 VMM(Step 06)이 프레임을 가상 주소에 붙이고, 맨 위 힙이 그 영역을 작게 잘라 씁니다.

새 파일은 `mm/heap.c`·`heap.h` 하나이고, `kernel/main.c` 에서 `heap_init()` 을 부르고 할당·해제를 시험합니다.
`heap.c` 를 위에서부터 `block_t` → `heap_init` → `kmalloc` → `kfree` → `heap_dump` 순서로 읽으면 됩니다.

## 힙 영역 준비: 12GB에 1MB

`heap_init()` 은 PMM에서 프레임 256개를 받아, 가상 주소 `0x300000000`(12GB)부터 연속으로 매핑합니다. 256 × 4KB = 1MB입니다.
물리 프레임들은 서로 떨어져 있을 수도 있지만, 가상 주소로는 12GB부터 1MB가 빈틈없이 이어집니다. 가상 메모리를 쓰는 이유가 바로 이것입니다. 힙 코드는 물리 메모리가 어떻게 흩어져 있든 신경 쓰지 않고, 연속된 1MB짜리 배열 하나를 다루듯 쓸 수 있습니다.
12GB라는 주소는 Step 06에서 정한 규칙을 따른 것입니다. 1GB 아래는 2MB 대형 페이지가 차지하고 있으니 피하고, Step 12에서 유저 프로그램이 쓸 16GB, 20GB와도 떨어진 곳을 골랐습니다.
이 크기는 최종 코드까지 1MB로 고정입니다. 프로세스 구조체, 커널 스택, 파일 버퍼가 전부 여기서 나오므로, 나중에 큰 파일을 읽거나 프로세스를 많이 만들면 이 1MB가 한계가 됩니다.

## 블록: 헤더와 데이터

힙 전체는 **블록** 들이 빈틈없이 이어진 모양입니다. 블록 하나는 24바이트 헤더와 그 뒤의 데이터 영역으로 이루어집니다.

```c
typedef struct block {
    uint64_t      size;  /* 데이터 크기 (헤더 제외) */
    uint64_t      used;  /* 1 = 사용 중, 0 = 빈 블록 */
    struct block *next;  /* 다음 블록 */
} block_t;
```

`next` 로 블록들이 연결 리스트를 이루고, 리스트를 따라가면 힙 전체를 처음부터 끝까지 훑을 수 있습니다. 처음에는 1MB 전체가 빈 블록 하나입니다.

```
[hdr | free  1MB - 24B ..........................................]
```

`kmalloc` 이 돌려주는 주소는 헤더 바로 뒤, 데이터 영역의 시작(`b + 1`)입니다. 거꾸로 `kfree(ptr)` 는 `ptr` 에서 헤더 크기만큼 뒤로 가서(`(block_t *)ptr - 1`) 그 블록의 헤더를 찾습니다. 그래서 `kfree` 는 크기를 따로 받지 않아도 됩니다.

## kmalloc: 처음 맞는 것을 골라 자르기

```c
void *kmalloc(uint64_t size) {
    size = ALIGN8(size);
    for (block_t *b = heap_start; b; b = b->next) {
        if (b->used || b->size < size) continue;
        if (b->size >= size + sizeof(block_t) + 8) {
            ... b 뒤쪽을 새 빈 블록으로 떼어 낸다 ...
        }
        b->used = 1;
        return (void *)(b + 1);
    }
    return NULL;
}
```

먼저 요청 크기를 8의 배수로 올립니다. 모든 블록 크기가 8의 배수이면 헤더(24바이트)도 데이터도 항상 8바이트 경계에 놓이고, 돌려주는 주소에 `uint64_t` 나 포인터를 안전하게 담을 수 있습니다.
그다음 리스트를 앞에서부터 훑어, 비어 있고 충분히 큰 **첫 번째** 블록을 고릅니다. 이 방식을 first-fit이라고 합니다. 가장 딱 맞는 블록을 찾는 best-fit보다 단순하고 빠르지만, 앞쪽에 작은 조각이 남기 쉽습니다.

고른 블록이 요청보다 많이 크다면 **분할** 합니다. 앞쪽 `size` 바이트만 쓰고, 그 바로 뒤에 새 헤더를 만들어 나머지를 빈 블록으로 떼어 냅니다. 분할하지 않으면 100바이트를 원하는 요청에 1MB 블록을 통째로 주게 됩니다.
다만 남는 부분이 새 헤더(24바이트)와 최소 데이터(8바이트)도 담지 못할 만큼 작으면 분할하지 않고 블록 전체를 줍니다. 몇 바이트 더 주는 편이 쓸모없는 조각을 만드는 것보다 낫기 때문입니다.
`kmalloc(100)` 과 `kmalloc(200)` 을 차례로 부른 뒤의 힙은 이렇게 됩니다(100은 104로 올림).

```
[hdr | used 104B][hdr | used 200B][hdr | free 나머지 ....................]
```

## kfree: 돌려받고, 뒤쪽과 합치기

`kfree` 는 블록의 `used` 를 0으로 바꿉니다. 그런데 그것만 하면 문제가 생깁니다. 작은 블록을 계속 할당하고 해제하다 보면 힙이 잘게 쪼개진 빈 블록들로 가득 차서, 전체 빈 공간은 충분한데 큰 요청을 들어줄 블록이 하나도 없는 상태가 됩니다. 이것을 **단편화** 라고 합니다.
그래서 해제할 때 **바로 뒤** 블록도 비어 있으면 둘을 하나로 **병합** 합니다. 뒤 블록의 헤더까지 내 데이터 영역에 흡수하고(`size += 24 + next->size`), 뒤 블록을 리스트에서 뺍니다.
이 구현은 앞쪽 블록과는 합치지 않습니다. 리스트가 한 방향으로만 연결되어 있어서, 내 앞의 블록이 누구인지 바로 알 수 없기 때문입니다. 그래서 해제 순서에 따라 결과가 달라집니다.
예를 들어 위 상태에서 `kfree(b)` 다음 `kfree(a)` 를 하면, b가 뒤의 빈 블록과 합쳐지고, 이어서 a가 그 합쳐진 블록과 합쳐져 다시 1MB짜리 블록 하나가 됩니다. 반대로 `kfree(a)` 를 먼저 하면, 그 순간 뒤의 b는 아직 사용 중이라 합칠 수 없습니다. 이어서 `kfree(b)` 를 하면 b는 뒤와 합쳐지지만, a는 이미 해제가 끝난 상태라 누구도 a를 b와 합쳐 주지 않습니다. 결과는 빈 블록 두 개입니다.

## 이 단계가 뒤에 남기는 것

`kmalloc` / `kfree` 는 이후 거의 모든 커널 객체의 출처가 됩니다. 프로세스 구조체와 커널 스택(08), 메모리 파일시스템의 노드(09), ELF 파일을 읽어 올 버퍼(18), fork한 자식의 구조체와 스택(20)이 모두 이 힙에서 나옵니다.
"PMM → VMM → 힙"의 3층 구조는 운영체제 메모리 관리의 기본 그림입니다. 앞으로 메모리가 필요할 때 어느 층에 부탁할지가 분명해집니다. 페이지 단위로 매핑해야 하는 것(페이지 테이블, 유저 페이지)은 PMM과 VMM을, 크기가 제각각인 커널 데이터는 힙을 씁니다.
`heap_dump()` 는 블록 수와 사용·여유 바이트를 출력하는 디버깅 도구로, 메모리 누수를 의심할 때 유용합니다.

## 직접 만들어 보기

`heap_init` 으로 1MB를 매핑하고 블록 하나를 만든 뒤, 분할 없이 블록을 통째로 주는 `kmalloc` 부터 만들어 보세요. 두 번째 호출이 `NULL` 을 돌려주는 것을 보면 분할이 왜 필요한지 바로 이해됩니다.
그다음 분할을 넣고, `kfree` 와 뒤쪽 병합을 넣습니다. 각 단계마다 `heap_dump()` 로 블록 수를 확인하세요.
여유가 있다면 앞쪽 병합도 시도해 보세요. 리스트를 처음부터 훑어 "내 앞 블록"을 찾거나, 헤더에 `prev` 포인터를 추가하는 두 가지 방법이 있습니다.

## 확인하기

부팅 로그에 다음과 같은 줄들이 나옵니다.

```
[heap] 1 MB at 0x0000000300000000
[test] a=0x0000000300000018 b=0x0000000300000098
[heap] blocks=3  used=304 B  free=... B
[heap] blocks=1  used=0 B  free=... B
```

`a` 가 `0x300000018` 인 것은 첫 헤더(24 = 0x18바이트) 바로 뒤이기 때문이고, `b` 는 `a` 의 데이터 104바이트와 다음 헤더 24바이트를 지난 곳입니다. 할당 후에는 블록이 3개, 둘 다 해제한 뒤에는 1개로 돌아옵니다.
`main.c` 에서 `kfree(b); kfree(a);` 의 순서를 바꿔 보면 마지막 줄이 `blocks=2` 로 바뀌는 것을 볼 수 있습니다.

## 막혔을 때

두 번째 `kmalloc` 이 첫 번째와 같은 주소를 준다면 `used = 1` 표시를 빠뜨린 것입니다.
리스트를 따라가다 페이지 폴트가 난다면 헤더가 깨진 것입니다. 할당받은 크기보다 많이 써서 다음 블록의 헤더를 덮어쓴 경우가 대부분이고, 이 버그는 앞으로도 자주 만나게 됩니다. 그럴 때 `heap_dump()` 를 불러 보면 어디서 리스트가 이상해지는지 찾는 데 도움이 됩니다.
1MB를 다 쓰지 않았는데 `NULL` 이 나온다면 병합이 동작하지 않아 조각만 남은 것입니다.
`heap_init` 에서 바로 멈춘다면 `vmm_map_page` 가 12GB 주소에 대해 중간 테이블을 만들지 못한 것이니 Step 06으로 돌아가 보세요.
