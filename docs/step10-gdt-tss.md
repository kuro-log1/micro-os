# Step 10 — GDT 유저 세그먼트 & TSS

> CPU에 "ring 3 코드/데이터 세그먼트"와, ring 3에서 커널로 들어올 때 갈아탈 커널 스택(TSS.rsp0)을 알려 준다.

## 목표

부팅 로그에 `[tss] loaded at ... rsp0=...` 이 나오고, 트리플 폴트 없이 셸까지 정상 진입한다. (눈에 보이는 기능은 아직 없음 — 준비 단계)

## 이 단계가 만드는 틀

- **셀렉터 약속** — 이후 ring 3 진입(14)과 fork 복귀(20)에서 쓰는 값
  | 셀렉터 | 의미 | ring 3에서 쓸 값 (RPL=3) |
  |---|---|---|
  | `0x08` | 커널 코드 | — |
  | `0x10` | 커널 데이터 | — |
  | `0x18` | 유저 코드 (DPL 3, 64비트) | `0x1B` |
  | `0x20` | 유저 데이터 (DPL 3) | `0x23` |
  | `0x28` | TSS (16바이트, GDT 두 칸 차지) | — |
- **TSS.rsp0 = "유저 → 커널 전환 시 쓸 스택"** — Step 14부터 ring 3에서 인터럽트가 걸릴 때마다 CPU가 이 값을 rsp로 로드한다.
  지금은 고정 4KB 스택 하나지만, Step 22에서 프로세스마다 바꿔 끼우게 된다 (`tss_set_rsp0`)

## 만들 파일

| 파일 | 역할 |
|---|---|
| `boot/boot.s` | `gdt64` 에 유저 코드 · 데이터 + TSS 빈칸 두 개 추가, `.global gdt64` |
| `kernel/tss.c` | 104바이트 TSS 구조체, `rsp0` 설정, GDT[5]/[6]에 시스템 디스크립터 기록, `ltr 0x28` |
| `kernel/main.c` | `tss_init()` |

원본 커밋: `67ba289` · 읽는 순서: `boot/boot.s`(gdt64) → `kernel/tss.c`

## 핵심 개념

- **권한 링**: x86은 ring 0(커널) ~ ring 3(유저). 현재 링(CPL)은 CS 셀렉터의 하위 2비트. 세그먼트 디스크립터의 DPL이 "누가 이 세그먼트를 쓸 수 있나"
- **64비트에서 세그먼트는 거의 의미 없다** — base/limit은 무시되고 **권한(DPL)과 64비트 플래그(L)** 만 중요. 그래서 디스크립터 값이 커널용과 DPL 비트만 다르다 (`0x9A` → `0xFA`)
- **왜 TSS?** ring 3 코드가 돌다 인터럽트가 오면, CPU는 유저 스택을 믿을 수 없으니 **커널 스택으로 바꾼 뒤** `ss, rsp, rflags, cs, rip` 를 push한다. 그 커널 스택 주소를 TSS.rsp0에서 읽는다
- **TSS 디스크립터는 16바이트** (주소가 64비트라 두 칸): 타입 `0x89` = 사용 가능한 64비트 TSS. base를 여러 조각으로 나눠 기록
- **`ltr`**: Task Register에 TSS 셀렉터 로드. 한 번만 하면 된다

## 직접 만든다면

1. boot.s GDT에 유저 세그먼트 두 줄 추가 — 그것만으로 부팅이 계속 되는지 확인
2. TSS 구조체 정의(packed, 104바이트)와 정적 커널 스택
3. GDT[5], [6]에 디스크립터 비트 조립 (주석의 비트 배치 표를 보며)
4. `ltr` — 디스크립터가 틀리면 여기서 바로 #GP

## 확인

- `[tss] loaded at 0x... rsp0=0x...` 출력 후 셸 정상 동작

## 자주 막히는 곳

| 증상 | 원인 |
|---|---|
| `ltr` 에서 General Protection | TSS 디스크립터 타입/Present 비트, base 조각 위치 틀림 |
| GDT를 늘렸더니 부팅 실패 | `gdt64_ptr` 의 limit 이 `gdt64_end - gdt64 - 1` 로 자동 계산되는지 확인 |
