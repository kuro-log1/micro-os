# Step 10 — GDT 유저 세그먼트 & TSS

Part 2의 목표는 유저 프로그램을 커널과 분리된 **ring 3** 에서 돌리는 것입니다. x86 CPU는 0부터 3까지 네 단계의 권한 수준(ring)을 갖고 있고, 현재 실행 중인 코드가 어느 ring인지에 따라 할 수 있는 일이 달라집니다. ring 0은 무엇이든 할 수 있고, ring 3은 특권 명령(`cli`, `hlt`, `lgdt`, 포트 I/O 등)을 실행할 수 없으며 커널 전용 메모리에도 접근할 수 없습니다.
ring 3 코드를 실행하려면 CPU에 몇 가지를 미리 알려 둬야 합니다. 이번 단계는 그 준비 단계로, 눈에 보이는 새 기능은 없습니다. 대신 두 가지를 깔아 둡니다.
첫째는 ring 3 코드가 사용할 **유저 코드·데이터 세그먼트** 를 GDT에 추가하는 것이고, 둘째는 ring 3에서 인터럽트가 걸려 커널로 들어올 때 CPU가 갈아탈 **커널 스택의 위치** 를 알려 주는 **TSS** 를 만드는 것입니다.
이 단계가 끝나면 부팅 로그에 `[tss] loaded at ... rsp0=...` 한 줄이 추가되고, 나머지는 이전과 똑같이 셸까지 동작합니다. 겉으로는 아무 변화가 없지만, 디스크립터 비트 하나만 틀려도 부팅이 즉시 실패하는 까다로운 단계입니다.

바뀌는 파일은 `boot/boot.s`(GDT 확장)이고, 새 파일은 `kernel/tss.c`·`tss.h` 입니다. `kernel/main.c` 에 `tss_init()` 이 추가됩니다.
`boot.s` 의 `gdt64` → `tss.c` 순서로 읽으세요.

## 64비트에서 세그먼트가 하는 일

Step 01-3에서 GDT를 만들 때, 64비트에서는 세그먼트의 base와 limit이 거의 무시된다고 했습니다. 그런데도 GDT가 필요한 이유는 **권한** 때문입니다.
현재 코드의 권한 수준(CPL)은 CS 레지스터에 담긴 셀렉터의 하위 2비트로 정해집니다. 그리고 세그먼트 디스크립터의 DPL(Descriptor Privilege Level) 필드가 "이 세그먼트는 어느 ring용인가"를 정합니다. ring 3 코드가 돌려면 DPL이 3인 코드 세그먼트를 CS에, DPL이 3인 데이터 세그먼트를 SS에 넣어야 합니다.
그래서 지금 GDT 뒤에 두 줄을 추가합니다.

```asm
.global gdt64
gdt64:
    .quad 0x0000000000000000    /* 0x00: null */
    .quad 0x00AF9A000000FFFF    /* 0x08: 커널 코드 (L=1, P=1, DPL=0) */
    .quad 0x00CF92000000FFFF    /* 0x10: 커널 데이터 (P=1, DPL=0, RW=1) */
    .quad 0x00AFFA000000FFFF    /* 0x18: 유저 코드  (L=1, P=1, DPL=3) */
    .quad 0x00CFF2000000FFFF    /* 0x20: 유저 데이터 (P=1, DPL=3, RW=1) */
    .quad 0x0000000000000000    /* 0x28: TSS 디스크립터 low  (tss_init이 채움) */
    .quad 0x0000000000000000    /* 0x30: TSS 디스크립터 high (tss_init이 채움) */
```

유저 코드와 데이터 디스크립터는 커널 것과 비교하면 접근 바이트 하나만 다릅니다. `0x9A` 가 `0xFA` 로, `0x92` 가 `0xF2` 로 바뀌었습니다. 접근 바이트의 bit 5~6이 DPL이고, `0x9` → `0xF` 는 그 두 비트를 모두 켜서 DPL을 0에서 3으로 바꾼 것입니다. 64비트 코드임을 뜻하는 L 비트는 유저 코드에도 그대로 켜져 있습니다.
`gdt64` 를 `.global` 로 공개한 것은 C 코드인 `tss.c` 가 GDT의 5, 6번 칸에 TSS 디스크립터를 직접 써 넣기 위해서입니다. 마지막 두 칸을 0으로 비워 둔 이유가 이것입니다.
Step 01-3에서 GDT 크기를 `gdt64_end - gdt64 - 1` 로 계산하게 해 두었기 때문에, 칸을 늘려도 `gdt64_ptr` 는 고칠 필요가 없습니다.

## 셀렉터와 RPL

이제 셀렉터는 다섯 종류가 됩니다. `0x08` 커널 코드, `0x10` 커널 데이터, `0x18` 유저 코드, `0x20` 유저 데이터, `0x28` TSS입니다.
그런데 Step 14에서 실제로 ring 3에 진입할 때는 `0x18`, `0x20` 이 아니라 `0x1B`, `0x23` 을 씁니다. 셀렉터의 하위 2비트는 RPL(Requested Privilege Level), "이 셀렉터를 어느 권한으로 쓰겠다"는 요청이고, ring 3에서 쓸 셀렉터는 RPL도 3이어야 하기 때문입니다. `0x18 | 3 = 0x1B`, `0x20 | 3 = 0x23` 입니다. 이 값들은 Step 12의 `usermode.h` 에 `USER_CS`, `USER_DS` 로 정의되어, Step 14의 ring 3 진입에서 쓰입니다.

## TSS: ring 3에서 커널로 들어올 때의 스택

ring 3 코드가 돌고 있을 때 타이머 인터럽트가 걸리면 어떻게 될까요? CPU는 인터럽트 프레임(rip, cs, rflags, rsp, ss)을 스택에 쌓아야 하는데, 지금 `rsp` 는 유저 프로그램의 스택을 가리키고 있습니다.
유저 스택은 믿을 수 없습니다. 유저 프로그램이 `rsp` 를 아무 값으로나 바꿔 놓았을 수도 있고, 커널 메모리를 가리키게 해서 커널을 공격할 수도 있습니다. 그래서 CPU는 권한이 낮은 곳에서 높은 곳으로 넘어가는 인터럽트가 오면, 프레임을 쌓기 **전에** 스택을 커널 스택으로 바꿉니다.
그 커널 스택의 주소를 CPU가 읽어 오는 곳이 **TSS(Task State Segment)** 의 `rsp0` 필드입니다. 이름의 "Task"는 32비트 시절 하드웨어 태스크 전환에 쓰이던 흔적이고, 64비트에서 TSS의 실질적인 역할은 이 스택 주소들을 담는 것뿐입니다.

```c
typedef struct {
    uint32_t reserved0;
    uint64_t rsp0, rsp1, rsp2;
    uint64_t reserved1;
    uint64_t ist1, ist2, ist3, ist4, ist5, ist6, ist7;
    uint64_t reserved2;
    uint16_t reserved3;
    uint16_t iomap_base;
} __attribute__((packed)) tss64_t;      /* 104바이트 */
```

`rsp0` 는 ring 0으로 들어올 때의 스택이고, `rsp1`, `rsp2` 는 ring 1, 2용이라 쓰지 않습니다. `ist1~7` 은 특정 인터럽트에 전용 스택을 주는 기능인데 역시 쓰지 않습니다. `iomap_base` 를 구조체 크기로 두는 것은 "I/O 포트 권한 비트맵이 없다"는 뜻으로, ring 3에서 포트에 접근하면 무조건 막히게 합니다.
`tss_init()` 은 4KB짜리 정적 배열 `syscall_stack` 을 만들어 그 꼭대기를 `rsp0` 에 넣습니다. 스택은 아래로 자라므로 배열의 끝 주소가 시작점입니다.

## TSS 디스크립터와 ltr

CPU에 TSS의 위치를 알려 주는 방법도 GDT를 거칩니다. TSS를 가리키는 특별한 **시스템 디스크립터** 를 GDT에 넣고, 그 셀렉터를 `ltr` 명령으로 Task Register에 넣습니다.
이 디스크립터는 일반 디스크립터와 달리 16바이트입니다. TSS의 주소가 64비트라서 8바이트 안에 다 들어가지 않기 때문이고, 그래서 GDT의 5번과 6번 칸을 함께 차지합니다.

```c
gdt64[5] = (limit & 0xFFFF)
         | ((base & 0xFFFFFF) << 16)
         | ((uint64_t)0x89 << 40)
         | (((limit >> 16) & 0xF) << 48)
         | (((base >> 24) & 0xFF) << 56);
gdt64[6] = (base >> 32) & 0xFFFFFFFF;
__asm__ volatile("ltr %0" : : "r"((uint16_t)0x28));
```

앞 8바이트에는 크기(limit)와 주소의 하위 32비트가 여러 조각으로 흩어져 들어가고, 뒤 8바이트에는 주소의 상위 32비트가 들어갑니다. 흩어진 모양은 Step 02의 IDT 게이트와 마찬가지로 32비트 시절 형식을 유지한 결과입니다. `tss.c` 의 주석에 비트 배치가 표로 정리되어 있으니 대조하며 읽어 보세요.
타입 바이트 `0x89` 는 Present=1, DPL=0, 타입 9(사용 가능한 64비트 TSS)입니다. `ltr 0x28` 은 "GDT의 0x28 위치에 있는 디스크립터가 TSS다"라고 CPU에 알립니다. 디스크립터가 조금이라도 틀리면 바로 이 명령에서 일반 보호 예외가 납니다. 다행히 Step 02 덕분에 이제는 재부팅 대신 패닉 메시지를 볼 수 있습니다.

`tss_set_rsp0(rsp)` 라는 함수도 미리 만들어 둡니다. 지금은 모든 ring 3 진입이 4KB 스택 하나를 함께 쓰는 구조인데, 유저 프로세스가 여럿이 되면 이것이 문제가 됩니다. Step 22에서 스케줄러가 프로세스를 바꿀 때마다 이 함수로 `rsp0` 를 그 프로세스의 커널 스택으로 바꿔 끼우게 됩니다.

## 이 단계가 뒤에 남기는 것

GDT의 셀렉터 배치(`0x08`/`0x10` 커널, `0x18`/`0x20` 유저, `0x28` TSS)가 최종 형태로 확정됩니다. ring 3에서 쓸 셀렉터 값은 RPL을 더한 `0x1B`/`0x23` 입니다.
"ring 3에서 인터럽트가 오면 CPU는 TSS.rsp0의 스택으로 갈아탄다"는 규칙은 Step 11의 시스템 콜, Step 14의 유저 모드 진입이 전제로 삼는 사실입니다. 이게 없으면 ring 3 코드가 시스템 콜을 부르는 순간 커널이 죽습니다.
`tss_set_rsp0()` 는 Step 22에서 프로세스별 커널 스택을 구현하는 열쇠가 됩니다.

## 직접 만들어 보기

먼저 `boot.s` 의 GDT에 유저 세그먼트 두 줄만 추가하고 부팅해 보세요. 아직 아무도 그 세그먼트를 쓰지 않으니 이전과 똑같이 동작해야 합니다.
다음으로 TSS 구조체를 정의하고, `sizeof(tss64_t)` 가 정확히 104인지 출력해 확인합니다. `packed` 를 빼면 컴파일러가 정렬을 위해 빈칸을 넣어 크기가 달라지는 것도 볼 수 있습니다.
그다음 디스크립터 비트를 조립합니다. `tss.c` 주석의 표를 옆에 두고 한 필드씩 써 넣는 것이 가장 안전합니다. 마지막으로 `ltr` 을 실행하고, QEMU 모니터의 `info registers` 에서 `TR=0028` 과 TSS의 주소가 보이는지 확인합니다.

## 확인하기

부팅 로그에 다음 줄이 추가되고, 셸은 이전과 똑같이 동작합니다.

```
[tss] loaded at 0x00000000001.....  rsp0=0x00000000001.....
```

## 막혔을 때

`ltr` 에서 General Protection 패닉이 난다면 TSS 디스크립터의 타입이나 Present 비트, 또는 base 조각의 위치가 틀린 것입니다. 에러 코드에 셀렉터 값(`0x28`)이 담겨 있을 것입니다.
GDT를 늘렸더니 부팅 자체가 안 된다면 `gdt64_ptr` 의 크기가 `gdt64_end - gdt64 - 1` 로 자동 계산되는지 확인하세요. 크기가 작으면 `ltr` 이 표 바깥을 읽습니다.
`ltr` 은 통과했는데 `info registers` 의 TR base가 엉뚱하다면 base를 자르는 시프트 값을 다시 보세요.
