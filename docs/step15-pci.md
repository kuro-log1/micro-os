# Step 15 — PCI 버스 스캔

Part 3의 목표는 디스크에 저장된 프로그램을 읽어 실행하는 것입니다. 그러려면 먼저 디스크와 이야기할 수 있어야 하고, 그 전에 **이 컴퓨터에 어떤 장치가 붙어 있는지** 를 알아야 합니다.
지금까지 다룬 장치들, 즉 VGA, 직렬 포트, PIC, PIT, PS/2 키보드는 모두 PC 초창기부터 정해진 포트 번호에 고정되어 있었습니다. 그래서 장치를 찾을 필요 없이 그 번호로 바로 이야기할 수 있었습니다. 하지만 디스크 컨트롤러, 네트워크 카드, 그래픽 카드 같은 현대의 장치들은 대부분 **PCI 버스** 에 꽂혀 있고, 어떤 장치가 어느 자리에 있는지는 컴퓨터마다 다릅니다.
이번 단계에서는 PCI 버스를 훑어 붙어 있는 장치들의 목록을 부팅 로그에 출력합니다. 아직 장치를 제어하지는 않습니다. 목록을 읽는 법을 익히고, 다음 단계가 다룰 디스크 컨트롤러가 PCI 위에서 어떤 자리에 있는지 알아 두는 것이 목적입니다.
이 단계는 원래 저장소의 커밋 `03c5032` 의 일부입니다.

바뀌는 파일은 `kernel/io.h`(32비트 포트 함수)이고, 새 파일은 `drivers/pci.c`·`pci.h` 입니다. `kernel/main.c` 에서 `pci_scan()` 을 부릅니다.
`kernel/io.h` → `drivers/pci.c` 순서로 읽으세요. 이번 단계는 짧습니다.

## PCI 설정 공간

PCI 장치는 각자 256바이트짜리 **설정 공간(configuration space)** 을 갖고 있습니다. 장치가 자기 자신에 대해 알려 주는 레지스터 묶음으로, 맨 앞에는 누가 만들었고(vendor ID) 무슨 제품인지(device ID)가, 그 뒤에는 장치의 종류(class code), 장치의 레지스터가 어느 주소에 있는지(BAR) 같은 정보가 들어 있습니다.
운영체제는 이 설정 공간을 읽어서 "이 자리에 인텔의 IDE 컨트롤러가 있다"는 식으로 장치를 알아보고, 알맞은 드라이버를 붙입니다.

장치의 자리는 세 숫자로 정해집니다. **버스** 번호(0~255), 그 버스 위의 **장치** 번호(0~31), 그리고 한 장치가 여러 기능을 가질 때의 **기능** 번호(0~7)입니다. 흔히 `00:01.1` 처럼 "버스:장치.기능"으로 적습니다.

## 0xCF8과 0xCFC로 읽기

설정 공간을 읽는 전통적인 방법은 두 개의 포트를 쓰는 것입니다. 포트 `0xCF8` 에 "어느 장치의 몇 번째 레지스터를 읽고 싶다"는 주소를 쓰고, 포트 `0xCFC` 에서 그 레지스터의 32비트 값을 읽습니다.

```c
uint32_t pci_read(uint8_t bus, uint8_t dev, uint8_t func, uint8_t off) {
    uint32_t addr = (1u << 31)              /* enable */
                  | ((uint32_t)bus  << 16)
                  | ((uint32_t)dev  << 11)
                  | ((uint32_t)func <<  8)
                  | (off & 0xFC);           /* 4바이트 정렬 */
    outl(0xCF8, addr);
    return inl(0xCFC);
}
```

주소의 bit 31은 "설정 공간 접근을 켠다"는 표시이고, 그 아래로 버스(8비트), 장치(5비트), 기능(3비트), 레지스터 오프셋(8비트)이 차례로 들어갑니다. 레지스터는 4바이트 단위로만 읽을 수 있어서 오프셋의 하위 2비트는 항상 0으로 지웁니다.
이 포트들은 32비트 단위로 읽고 써야 하므로, `kernel/io.h` 에 `outl` / `inl` 을 추가합니다. Step 01-4의 `outb` / `inb` 와 같은 모양에 명령만 `outl`, `inl` 로 바뀝니다. 이렇게 `io.h` 는 장치가 늘어날 때마다 필요한 크기의 포트 함수가 하나씩 덧붙는 공용 도구가 됩니다. 다음 단계에서는 16비트 함수가 추가됩니다.

## 버스 0 훑기

`pci_scan()` 은 버스 0의 장치 0~31을 차례로 확인합니다. 각 자리에서 오프셋 `0x00` 을 읽으면 하위 16비트가 vendor ID, 상위 16비트가 device ID입니다. vendor ID가 `0xFFFF` 면 그 자리는 비어 있습니다. 존재하지 않는 장치를 읽으면 버스가 모든 비트를 1로 돌려주기 때문입니다.
장치가 있으면 오프셋 `0x08` 을 읽어 클래스 코드를 꺼냅니다. 최상위 바이트가 큰 분류(base class), 그다음 바이트가 세부 분류(subclass)입니다. 예를 들어 base `0x01` 은 저장 장치이고, 그중 sub `0x01` 이 IDE 컨트롤러입니다. `0x02/0x00` 은 이더넷, `0x03/0x00` 은 VGA, `0x06/0x00` 은 호스트 브리지입니다. `class_name()` 이 이 표를 이름으로 바꿔 줍니다.
그리고 `[pci]   00:01.0  ISA bridge  [8086:7000]` 같은 줄을 출력합니다. Step 13에서 추가된 `%02x` 형식이 장치 번호를 두 자리로 맞춰 줍니다.

이 코드는 일부러 단순하게 만들어져 있습니다. **버스 0만, 기능 0만** 봅니다. 실제 컴퓨터에는 PCI 브리지 뒤에 다른 버스가 있을 수 있고, 한 장치가 여러 기능을 가질 수도 있습니다. QEMU의 기본 머신(i440FX)은 모든 장치가 버스 0에 있어서 이 정도로도 충분합니다.
한 가지 재미있는 점은, QEMU의 IDE 컨트롤러는 사실 장치 1의 **기능 1**(`00:01.1`)이라는 것입니다. 장치 1의 기능 0은 ISA 브리지입니다. 그래서 이 스캔에서는 IDE 컨트롤러가 직접 보이지 않을 수 있습니다. 기능 번호까지 도는 루프를 추가하는 것이 아래의 연습 문제입니다.

## 왜 디스크 전에 PCI를 보나

다음 단계의 ATA 드라이버는 사실 PCI를 거치지 않고, 오래된 고정 포트(`0x1F0` 등)로 디스크와 이야기합니다. IDE 컨트롤러는 호환성을 위해 그 포트들을 계속 지원하기 때문입니다.
그런데도 PCI 스캔을 먼저 하는 이유는, 현대의 장치를 다루는 출발점이 항상 이 과정이기 때문입니다. AHCI(SATA) 디스크, virtio 장치, 네트워크 카드 드라이버를 만든다면 "PCI에서 장치를 찾고 → 설정 공간의 BAR에서 레지스터 주소를 읽고 → 그 주소로 장치를 제어한다"는 순서를 밟게 됩니다. `pci_read` 는 그 첫 단계의 도구입니다.

## 이 단계가 뒤에 남기는 것

`pci_read(bus, dev, func, off)` 는 PCI 장치를 찾고 설정을 읽는 기본 도구입니다. 지금은 목록 출력에만 쓰이지만, 새 장치 드라이버를 붙일 때 가장 먼저 쓰게 될 함수입니다.
`kernel/io.h` 에 32비트 포트 함수 `outl` / `inl` 이 추가됐습니다.
부팅 로그의 장치 목록은 "이 커널이 어떤 하드웨어 위에서 돌고 있는가"를 알려 주는 정보로 남습니다.

## 직접 만들어 보기

`outl` / `inl` 을 만들고, `pci_read(0, 0, 0, 0)` 하나만 출력해 보세요. QEMU에서는 호스트 브리지인 `8086:1237` 이 나옵니다.
다음으로 0~31을 도는 루프를 만들고 빈 자리를 건너뜁니다. 그다음 클래스 코드를 꺼내 이름표를 붙입니다.
여유가 있다면 기능 번호 0~7까지 도는 루프로 확장해 보세요. 오프셋 `0x0C` 의 bit 23(헤더 타입의 bit 7)이 켜진 장치만 여러 기능을 가지므로, 그 장치만 기능 1~7을 확인하면 됩니다. 그러면 `00:01.1  IDE controller  [8086:7010]` 이 목록에 나타날 것입니다.

## 확인하기

부팅 로그에 다음과 비슷한 장치 목록이 나옵니다.

```
[pci] scanning bus 0...
[pci]   00:00.0  Host bridge  [8086:1237]
[pci]   00:01.0  ISA bridge  [8086:7000]
[pci]   00:02.0  VGA controller  [1234:1111]
[pci]   00:03.0  Ethernet controller  [8086:100e]
```

정확한 목록은 QEMU 버전과 옵션에 따라 다를 수 있습니다.

## 막혔을 때

모든 자리가 `ffff` 로 나와 아무 장치도 보이지 않는다면 주소의 bit 31(enable)을 빠뜨린 것입니다.
값이 엉뚱하게 나온다면 오프셋의 하위 2비트를 지우지 않았거나(`& 0xFC`), 시프트 값(16, 11, 8)이 틀린 것입니다.
`outl` 에서 컴파일 오류가 난다면 인라인 어셈블리의 피연산자 크기를 확인하세요. 값은 `eax`(`"a"` 제약에 32비트 변수)에, 포트는 `dx`(`"Nd"`)에 있어야 합니다.
