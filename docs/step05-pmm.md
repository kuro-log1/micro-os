# Step 05 — 물리 메모리 관리 (PMM, 비트맵)

지금까지 커널이 쓴 메모리는 전부 컴파일할 때 크기가 정해진 것들이었습니다. 16KB 스택, 256칸 키보드 버퍼, 페이지 테이블 세 장 모두 `.bss` 에 미리 자리를 잡아 둔 전역 변수입니다.
하지만 앞으로 만들 것들은 실행해 봐야 얼마나 필요한지 압니다. 프로세스를 몇 개 띄울지, 파일을 얼마나 읽을지, 페이지 테이블이 몇 장 필요할지는 미리 정할 수 없습니다. 실행 중에 메모리를 빌리고 돌려줄 수 있어야 합니다.
이번 단계에서는 그 가장 밑바닥, **물리 메모리 관리자(PMM)** 를 만듭니다. RAM을 4KB 조각(**프레임**)으로 나눠, 비어 있는 프레임을 하나 빌려 주는 `pmm_alloc_page()` 와 돌려받는 `pmm_free_page()` 를 제공합니다.
이후 커널이 쓰는 모든 동적 메모리는 결국 여기서 나옵니다. 페이지 테이블(06), 힙(07), 프로세스 스택(08), 유저 프로그램의 페이지(14·18), fork로 복사한 페이지(20)까지 전부입니다.

새 파일은 `kernel/multiboot2.h`(GRUB이 넘겨준 정보의 구조)와 `mm/pmm.c`·`pmm.h` 이고, `kernel/main.c` 에서 `pmm_init(info)` 를 부르고 할당·해제를 시험해 봅니다.
`multiboot2.h` 로 데이터 구조를 먼저 보고, `pmm.c` 의 `pmm_init` → `pmm_alloc_page` → `pmm_free_page` 순서로 읽으세요.

## RAM은 연속된 한 덩어리가 아니다

512MB RAM이 있다고 해서 주소 0부터 512MB까지가 전부 쓸 수 있는 메모리인 것은 아닙니다. 1MB 아래에는 BIOS가 쓰는 데이터와 VGA 메모리, ROM이 섞여 있고, 4GB 근처에는 장치들의 레지스터가 메모리처럼 보이는 영역(MMIO)이 있습니다. 이런 곳에 아무 데이터나 쓰면 장치가 오동작하거나 값이 사라집니다.
어디가 진짜 RAM이고 어디가 구멍인지는 펌웨어(BIOS)가 알고 있고, GRUB은 그 정보를 **메모리 맵** 으로 정리해 multiboot2 정보 구조체에 담아 줍니다. Step 01-2에서 `ebx` 를 `mb_info` 에 저장하고, Step 01-3에서 `kernel_main` 의 두 번째 인자 `info` 로 넘긴 바로 그 주소입니다. 드디어 이 값을 쓸 때가 왔습니다.

## multiboot2 정보 구조 읽기

정보 구조체는 8바이트 헤더(전체 크기와 예약 필드) 뒤에 **태그** 들이 줄지어 있는 모양입니다. 태그마다 앞에 `type` 과 `size` 가 있고, 그 뒤에 태그 종류별 내용이 옵니다. 부트로더 이름, 커맨드 라인, 메모리 맵, 프레임버퍼 정보 같은 것들이 각각 하나의 태그입니다. type 0인 태그가 나오면 목록이 끝납니다.
그래서 원하는 태그를 찾으려면 처음부터 하나씩 건너뛰며 type을 확인해야 합니다. 이때 한 가지 규칙이 있는데, **모든 태그는 8바이트 경계에서 시작한다** 는 것입니다. 태그의 `size` 는 패딩을 뺀 실제 크기라서, 다음 태그의 주소는 `size` 만큼 간 뒤 8의 배수로 올림해야 합니다.

```c
struct mb2_tag *tag = (struct mb2_tag *)(mb2_info + 8);
while (tag->type != MB2_TAG_END) {
    if (tag->type == MB2_TAG_MMAP) { ... }
    tag = (struct mb2_tag *)(((uint64_t)tag + tag->size + 7) & ~7UL);
}
```

`+ 7` 하고 `& ~7` 하는 것은 8의 배수로 올림하는 흔한 비트 연산입니다. 이 정렬을 빠뜨리면 태그 경계가 어긋나서 메모리 맵 태그를 지나쳐 버립니다.
메모리 맵 태그(type 6) 안에는 엔트리들이 `entry_size` 간격으로 이어집니다. 각 엔트리는 시작 주소(`base_addr`), 길이(`length`), 종류(`type`)를 가지며, 종류가 1이면 "사용 가능한 RAM"입니다. 엔트리 크기를 구조체 크기로 가정하지 않고 태그에 적힌 `entry_size` 를 쓰는 이유는, 규격이 나중에 필드를 늘려도 깨지지 않게 하기 위해서입니다.
이렇게 "태그 목록을 돌며 원하는 type을 찾는" 패턴은 Step 13의 `mmap_log` 에서도 똑같이 쓰입니다.

## 비트맵: 프레임 하나에 1비트

빌려 줄 수 있는 프레임을 어떻게 기억할까요? 가장 단순한 방법은 프레임마다 1비트를 두는 **비트맵** 입니다. 이 구현에서 비트가 1이면 비어 있고, 0이면 사용 중이거나 쓸 수 없는 프레임입니다.
4GB를 4KB로 나누면 프레임이 약 100만(1M) 개이고, 1M 비트는 128KB입니다. 이 배열 `bitmap[]` 은 커널의 `.bss` 에 들어갑니다. 우리 QEMU는 512MB뿐이라 대부분의 비트가 0으로 남지만, 4GB까지는 고칠 필요 없이 다룰 수 있습니다.

```c
static inline void page_set(uint64_t p)   { bitmap[p / 8] |=  (1 << (p % 8)); }
static inline void page_clear(uint64_t p) { bitmap[p / 8] &= ~(1 << (p % 8)); }
static inline int  page_test(uint64_t p)  { return (bitmap[p / 8] >> (p % 8)) & 1; }
```

프레임 번호 `p` 의 비트는 `p / 8` 번째 바이트의 `p % 8` 번째 비트입니다. 물리 주소는 `p * 4096` 이고, 거꾸로 주소를 4096으로 나누면 프레임 번호가 됩니다.

## pmm_init: 지도를 비트맵에 옮기기

`pmm_init` 은 메모리 맵의 "사용 가능" 엔트리마다 그 범위의 프레임을 비트맵에 1로 표시합니다. 두 가지를 조심합니다.
첫째, **영역의 경계를 프레임 경계에 맞춥니다.** 시작 주소는 올림하고 끝 주소는 내림합니다. 영역이 프레임 중간에서 시작하거나 끝나면, 그 프레임의 일부는 사용 가능한 RAM이 아니라는 뜻이니 통째로 쓰지 않습니다.
둘째, **커널 자신을 빌려 주지 않습니다.** 커널의 코드와 데이터, 스택, 페이지 테이블, 그리고 이 비트맵 자체도 사용 가능한 RAM 위에 있습니다. 이 프레임들을 빌려 주면 커널이 자기 몸을 덮어쓰게 됩니다. 그래서 Step 01-1의 링커 스크립트가 만들어 둔 `_kernel_end` 심볼을 읽어, 그보다 아래 프레임은 전부 사용 중으로 둡니다. 1MB 아래 영역도 자연스럽게 여기에 포함됩니다.
결과로 전체 프레임 수(`total`)와 빌려 줄 수 있는 프레임 수(`free`)를 출력합니다.

한 가지 알아 둘 한계가 있습니다. 이 구현은 GRUB이 만든 정보 구조체가 놓인 프레임은 따로 보호하지 않습니다. GRUB이 그 구조체를 커널 바로 뒤에 둔다면 첫 할당에서 덮어쓸 수 있습니다. 그래서 이 커널은 정보 구조체를 읽는 일(`mmap_log`, `pmm_init`)을 다른 할당보다 먼저 끝내고, 그 뒤로는 다시 읽지 않습니다.

## 빌리고 돌려주기

`pmm_alloc_page()` 는 비트맵을 앞에서부터 훑어 처음 만나는 1인 비트를 0으로 바꾸고, 그 프레임의 물리 주소를 돌려줍니다. 비어 있는 프레임이 없으면 `NULL` 입니다. `pmm_free_page(addr)` 는 반대로 그 프레임의 비트를 1로 되돌립니다. 이미 비어 있는 프레임을 또 해제하면 아무 일도 하지 않습니다.
처음부터 훑는 선형 탐색이라 메모리가 커질수록 느려지지만, 지금은 단순함이 더 중요합니다. 진짜 운영체제는 버디 할당기 같은 더 빠른 구조를 씁니다.

돌려받은 주소는 **물리 주소** 인데, 커널은 이 값을 그대로 포인터로 써서 그 메모리를 읽고 씁니다. 원래 페이징이 켜진 상태에서는 가상 주소만 쓸 수 있지만, Step 01-3에서 0~1GB를 아이덴티티 매핑해 두었기 때문에 1GB 아래의 물리 주소는 같은 값의 가상 주소로도 유효합니다.
이 약속이 성립하려면 모든 RAM이 1GB 안에 있어야 합니다. QEMU를 `-m 512M` 으로 띄우는 진짜 이유가 이것입니다. RAM을 2GB로 주면 PMM이 1GB 위의 프레임을 빌려 줄 수 있고, 그 주소를 포인터로 쓰는 순간 페이지 폴트가 납니다.

## 이 단계가 뒤에 남기는 것

`pmm_alloc_page()` / `pmm_free_page()` 는 커널의 모든 메모리의 원천이 됩니다. 앞으로 등장하는 할당은 거슬러 올라가면 전부 이 두 함수로 이어집니다.
"PMM이 준 물리 주소는 그대로 포인터로 쓸 수 있다"는 성질은 Step 06에서 페이지 테이블을 새로 만들 때 결정적으로 쓰입니다. 새 테이블용 프레임을 받자마자 그 주소에 바로 0을 채워 넣을 수 있기 때문입니다.
multiboot2 태그를 도는 방법은 Step 13의 메모리 맵 로그가 그대로 재사용합니다.

## 직접 만들어 보기

먼저 `multiboot2.h` 의 구조체를 정의하고, 태그를 돌면서 type과 size만 출력해 보세요. 어떤 태그들이 오는지 보는 것만으로도 GRUB이 무엇을 알려 주는지 감이 옵니다.
다음으로 메모리 맵 엔트리의 시작 주소, 길이, 종류를 출력해 보세요. QEMU 512MB에서는 1MB 아래의 작은 영역 하나, 1MB부터 512MB 근처까지의 큰 영역 하나, 그리고 예약된 영역 몇 개가 나올 것입니다.
그다음 비트맵과 세 개의 인라인 함수를 만들고, 사용 가능 영역을 표시합니다. 마지막으로 alloc/free를 만들어, 해제한 프레임이 다음 할당에서 다시 나오는지 확인합니다.

## 확인하기

부팅 로그에 다음과 비슷한 줄들이 나옵니다.

```
[pmm] total: 511 MB  free: 50x MB  (...pages)
[test] alloc a=0x0000000000xxx000 b=0x0000000000yyy000
[test] free a, alloc again=0x0000000000xxx000
```

`total` 과 `free` 의 차이가 커널이 차지한 크기(1MB 아래 포함)입니다. 두 번째 줄의 `a` 와 `b` 는 `_kernel_end` 바로 뒤의 연속된 프레임이고, 세 번째 줄에서 `a` 를 해제한 뒤 다시 할당하면 같은 주소가 나와야 합니다.

## 막혔을 때

`total` 이 0으로 나온다면 태그를 돌다 메모리 맵 태그를 지나친 것입니다. 8바이트 정렬 계산과, 첫 태그가 `info + 8` 에서 시작하는지 확인하세요.
할당받은 주소에 쓰자마자 커널이 이상하게 동작한다면 커널 영역을 사용 가능으로 표시한 것입니다. `_kernel_end` 비교를 빠뜨리지 않았는지 보세요.
할당받은 주소에 접근하자 페이지 폴트가 난다면 1GB가 넘는 주소일 가능성이 큽니다. QEMU의 `-m` 옵션이 1GB 미만인지 확인하세요.
`info` 가 0이거나 이상한 값이라면 Step 01-2/01-3에서 `ebx` 를 저장하고 `rsi` 로 넘기는 부분을 다시 보세요.
