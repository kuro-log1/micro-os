# Step 02 — IDT & CPU 예외 처리

Step 01의 커널은 잘 돌아가는 동안에는 문제가 없지만, 무언가 잘못되는 순간 아무런 흔적 없이 재부팅됩니다.
CPU는 0으로 나누기, 존재하지 않는 메모리 접근, 잘못된 명령 같은 사건을 만나면 **예외** 를 일으킵니다. 예외가 나면 CPU는 "예외 번호에 해당하는 처리 함수"로 점프하려고 하는데, 그 함수가 어디 있는지 적힌 표가 없으면 또 다른 예외(Double Fault)를 일으키고, 그것마저 처리할 수 없으면 트리플 폴트로 리셋해 버립니다.
이번 단계에서는 그 표, **IDT(Interrupt Descriptor Table)** 를 만들고, 예외가 나면 그 순간의 레지스터 값을 화면에 보여 주고 멈추는 `panic` 을 만듭니다.
이 단계의 진짜 가치는 예외 처리 자체보다, 여기서 정하는 **"커널에 들어오는 모든 길의 공통 모양"** 에 있습니다. 하드웨어 인터럽트(Step 03), 시스템 콜(Step 11), fork(Step 20)가 전부 이번에 만드는 틀 위에 그대로 올라갑니다.

새 파일은 `kernel/idt.h`, `kernel/idt_asm.s`, `kernel/idt.c`, `kernel/panic.c`·`panic.h` 이고, `kernel/main.c` 에 `idt_init()` 이 추가됩니다.
`idt.h`(구조체) → `idt_asm.s`(스텁) → `idt.c`(표 채우기) → `panic.c` 순서로 읽으면 흐름이 자연스럽습니다.

## IDT는 "번호 → 점프할 곳" 표

x86 CPU는 0번부터 255번까지 256개의 인터럽트 번호를 다룹니다. 그중 0~31번은 CPU가 스스로 일으키는 예외용으로 예약되어 있습니다. 0번이 0으로 나누기, 6번이 잘못된 명령, 13번이 일반 보호 예외(General Protection), 14번이 페이지 폴트입니다.
IDT는 이 256개 번호마다 "이 인터럽트가 오면 어느 코드로 갈지"를 적어 둔 표이고, 64비트 모드에서 칸 하나(게이트)는 16바이트입니다.

```c
typedef struct {
    uint16_t offset_low;    /* 핸들러 주소 [15:0]  */
    uint16_t selector;      /* 핸들러가 실행될 코드 세그먼트 = 0x08 */
    uint8_t  ist;
    uint8_t  type_attr;     /* 0x8E */
    uint16_t offset_mid;    /* 핸들러 주소 [31:16] */
    uint32_t offset_high;   /* 핸들러 주소 [63:32] */
    uint32_t zero;
} __attribute__((packed)) idt_gate_t;
```

핸들러 주소가 세 조각으로 쪼개져 들어가는 모양이 이상해 보이지만, 32비트 시절의 8바이트 게이트 형식을 유지한 채 64비트로 늘리다 보니 생긴 역사적 흔적입니다. `idt_set_gate(n, fn)` 이 주소를 잘라서 세 칸에 나눠 담습니다.
셀렉터 `0x08` 은 Step 01-3에서 만든 64비트 커널 코드 세그먼트입니다. "핸들러는 커널 권한의 64비트 코드로 실행하라"는 뜻입니다.
`type_attr` 의 `0x8E` 는 비트로 풀면 Present=1, DPL=0, 타입=0xE(64비트 인터럽트 게이트)입니다. 인터럽트 게이트로 들어가면 CPU가 자동으로 인터럽트 플래그(IF)를 꺼 주기 때문에, 핸들러가 도는 도중 다른 인터럽트가 끼어들지 않습니다. DPL 0은 "ring 0 코드만 `int n` 명령으로 이 게이트를 부를 수 있다"는 뜻인데, 이 값은 Step 11에서 시스템 콜용 게이트를 따로 열 때 다시 등장합니다.
표를 다 채우면 `lidt` 명령으로 표의 위치와 크기를 CPU에 알려 줍니다. GDT를 `lgdt` 로 등록했던 것과 같은 방식입니다.

## 스텁: 모든 예외를 같은 모양으로 맞추기

IDT의 각 칸이 C 함수를 직접 가리키면 안 될까요? 안 됩니다. 예외가 나는 순간 CPU는 몇 가지 값만 스택에 쌓고 핸들러로 점프할 뿐, 범용 레지스터는 저장해 주지 않습니다. C 함수는 레지스터를 마음대로 쓰기 때문에, 예외가 끝나고 원래 코드로 돌아갔을 때 레지스터가 엉망이 됩니다.
그래서 IDT의 칸은 작은 어셈블리 조각인 **스텁** 을 가리키고, 스텁이 레지스터를 모두 저장한 뒤 C 함수를 부릅니다.

여기에 한 가지 골치 아픈 사정이 더 있습니다. 예외 중 8, 10~14, 17번은 CPU가 원인을 알려 주는 **에러 코드** 를 하나 더 스택에 쌓고, 나머지는 쌓지 않습니다. 스택 모양이 예외마다 다르면 C 쪽에서 하나의 구조체로 읽을 수 없습니다.
해결책은 간단합니다. 에러 코드가 없는 예외의 스텁은 가짜 0을 대신 쌓아 줍니다.

```asm
.macro ISR_NOERR num
isr\num:
    pushq $0        /* 가짜 에러코드 */
    pushq $\num     /* 예외 번호 */
    jmp isr_common
.endm

.macro ISR_ERR num
isr\num:
    pushq $\num     /* 에러코드는 CPU가 이미 push */
    jmp isr_common
.endm
```

어셈블러 매크로로 두 가지 모양을 정의하고, 0~31번에 대해 하나씩 펼칩니다. 어느 쪽이든 `isr_common` 에 도착했을 때 스택 맨 위에는 예외 번호, 그 아래에는 에러 코드가 있게 됩니다.

`isr_common` 은 범용 레지스터 15개를 전부 쌓고, 지금의 스택 포인터를 첫 번째 인자(`rdi`)로 C 함수 `exception_handler` 를 부릅니다. C 함수가 돌아오면 쌓은 순서의 역순으로 레지스터를 꺼내고, 예외 번호와 에러 코드 16바이트를 건너뛴 뒤 `iretq` 로 원래 코드에 돌아갑니다.
이 순간 스택의 모습을 높은 주소부터 그려 보면 이렇습니다.

```
ss, rsp            ← CPU가 push (64비트 모드에서는 항상)
rflags, cs, rip    ← CPU가 push
err_code           ← CPU 또는 스텁의 가짜 0
int_no             ← 스텁
rax, rbx, ... r15  ← isr_common (r15가 가장 낮은 주소)
                   ← 여기가 rsp, C 함수가 받는 registers_t*
```

## registers_t: 스택을 구조체로 읽기

C 쪽에서는 이 스택 덩어리를 구조체 하나로 봅니다.

```c
typedef struct {
    uint64_t r15, r14, r13, r12, r11, r10, r9, r8;
    uint64_t rbp, rdi, rsi, rdx, rcx, rbx, rax;
    uint64_t int_no, err_code;
    uint64_t rip, cs, rflags;
} __attribute__((packed)) registers_t;
```

구조체의 첫 필드가 가장 낮은 주소에 놓이므로, 필드 순서는 **push 순서의 정반대** 여야 합니다. 마지막에 push한 r15가 첫 필드이고, 맨 처음 push한 rax가 범용 레지스터 중 마지막 필드입니다. 이 대응이 한 칸이라도 어긋나면 모든 레지스터 값이 한 칸씩 밀려서 보입니다.
CPU가 쌓은 `ss` 와 `rsp` 는 `rflags` 바로 위에 있지만 이 구조체에는 필드가 없습니다. 지금은 쓸 일이 없기 때문입니다. 그래도 스택에는 분명히 있고, `iretq` 는 다섯 값(rip, cs, rflags, rsp, ss)을 모두 꺼냅니다. Step 20의 fork는 이 다섯 값을 포함한 22워드를 통째로 복사하게 되는데, 그때 "구조체에는 없지만 스택에는 있는" 두 워드가 중요해집니다.

이 `registers_t` 는 이 단계에서 가장 중요한 산출물입니다. 앞으로 커널에 들어오는 모든 경로, 즉 예외와 IRQ와 시스템 콜이 똑같은 스택 모양을 만들고 똑같이 `registers_t*` 를 C 함수에 넘깁니다. 그래서 시스템 콜 핸들러는 `r->rax` 로 시스템 콜 번호를 읽고, `r->rax` 에 값을 써서 결과를 돌려주며, fork는 이 구조체를 복사해 자식 프로세스를 만듭니다.

## panic: 마지막 보고서

`exception_handler` 는 예외 번호로 이름표(`"Divide by Zero"`, `"Page Fault"` …)를 찾아 `panic` 을 부릅니다. `panic` 은 예외 이름, 번호, 에러 코드, 그리고 `rip` 와 주요 레지스터를 출력한 뒤 `cli; hlt` 로 영원히 멈춥니다.
이 중에서 가장 중요한 값은 `rip` 입니다. 예외를 일으킨 명령의 주소이기 때문에, `objdump -d iso/boot/kernel.elf` 에서 그 주소를 찾으면 어느 함수의 어느 줄에서 문제가 났는지 바로 알 수 있습니다. 앞으로 커널이 죽을 때마다 이 습관이 여러분을 구해 줄 것입니다.
지금은 모든 예외가 곧 패닉이지만, 나중에는 예외 번호에 따라 다르게 반응하게 됩니다. Step 06에서는 페이지 폴트일 때 문제가 된 주소(CR2)와 원인을 풀어서 보여 주는 코드가 이 핸들러에 덧붙습니다.

## 이 단계가 뒤에 남기는 것

"어셈블리 스텁이 스택 모양을 맞추고 → 공통 루틴이 레지스터를 저장하고 → C 핸들러가 `registers_t*` 를 받는다"는 패턴이 생겼습니다. Step 03의 IRQ 스텁과 Step 11의 시스템 콜 스텁은 이 모양을 복사해서 번호와 호출할 C 함수만 바꿉니다.
`idt_set_gate(n, fn)` 은 IDT에 칸을 채우는 유일한 방법으로 계속 쓰이고, `panic` 은 이후 모든 단계에서 "여기 오면 끝" 지점이자 디버깅의 출발점이 됩니다.
IDT의 0~31번이 예외라는 배치도 이후 약속의 시작입니다. Step 03에서 하드웨어 인터럽트는 32~47번에, Step 11에서 시스템 콜은 0x80(128)번에 자리 잡습니다.

## 직접 만들어 보기

게이트 구조체와 `lidt` 만 먼저 만들고, 모든 칸이 비어 있는 IDT를 로드해 보세요. 부팅이 정상적으로 되어야 합니다. 예외가 나지 않는 한 IDT는 읽히지 않기 때문입니다.
다음으로 `isr0` 스텁 하나와 `isr_common`, 예외 번호만 출력하는 `exception_handler` 를 만들고, 0으로 나누기로 시험합니다.
그다음 `registers_t` 를 정의하고 `rip` 를 출력해 보세요. 일부러 필드 순서를 하나 틀리게 해서 값이 엉뚱하게 나오는 것을 보는 것도 좋은 공부입니다.
마지막으로 매크로로 32개 스텁을 모두 만들고 에러 코드가 있는 예외를 구분한 뒤, 이름표와 `panic` 을 붙입니다.

## 확인하기

`kernel/main.c` 에 주석으로 남겨 둔 `/* volatile int zero = 0; printf("%d\n", 1 / zero); */` 의 주석을 풀고 실행하면 다음과 같은 화면이 나옵니다.

```
*** KERNEL PANIC: Divide by Zero ***
  int=0  err=0x0
  rip=0x00000000001.....  rflags=0x...
  ...
```

`rip` 값을 `objdump -d` 결과에서 찾아보면 `kernel_main` 안의 `idiv` 명령이 나올 것입니다. 주석을 다시 닫으면 평소처럼 부팅합니다.

## 막혔을 때

예외를 일으켰는데도 패닉 대신 재부팅된다면 IDT가 제대로 로드되지 않은 것입니다. `idtr.limit` 이 `sizeof(idt) - 1` 인지, 게이트의 셀렉터가 `0x08` 인지, 주소를 세 조각으로 나누는 시프트가 맞는지 확인하세요.
레지스터 값이 한 칸씩 밀려 보인다면 push 순서와 `registers_t` 필드 순서가 맞지 않거나, 에러 코드가 있는 예외를 `ISR_NOERR` 로 만든 것입니다.
`1 / zero` 가 아무 일 없이 지나간다면 컴파일러가 상수 계산으로 나눗셈을 없애 버린 것입니다. `zero` 를 `volatile` 로 선언해야 실제 나눗셈 명령이 남습니다.
