# Step 06 — 가상 메모리 & 4단계 페이징 (VMM)

앞 단계에서 물리 프레임을 빌릴 수 있게 됐지만, 그 프레임은 아이덴티티 매핑 덕분에 물리 주소와 같은 값의 가상 주소로만 쓸 수 있었습니다.
운영체제가 가상 메모리를 쓰는 이유는 바로 이 고정된 대응을 깨기 위해서입니다. 커널의 힙은 커널 코드와 멀리 떨어진 넓은 주소 공간에 두고 싶고, 유저 프로그램은 모두 같은 주소(예: 16GB)에서 시작하게 하되 실제로는 각자 다른 물리 메모리를 쓰게 하고 싶습니다. 이 모든 것이 "원하는 가상 주소에 원하는 물리 프레임을 붙이는" 한 가지 능력에서 나옵니다.
이번 단계에서는 그 능력, `vmm_map_page(pml4, virt, phys, flags)` 를 만듭니다. 그리고 가상 주소 `0x400000000`(16GB), 즉 지금까지 아무것도 없던 주소에 프레임을 붙여 실제로 값을 쓰고 읽어 봅니다.
매핑이 없는 곳에 접근하면 페이지 폴트가 나는데, 그때 "어느 주소에서, 왜" 났는지 보여 주는 진단 메시지도 함께 만듭니다. 이 메시지는 앞으로 만나게 될 메모리 버그 대부분을 잡아 주는 도구가 됩니다.

새 파일은 `mm/vmm.c`·`vmm.h` 입니다. `kernel/idt.c` 의 예외 핸들러에 페이지 폴트 진단이 추가되고, `kernel/main.c` 에서 매핑을 시험합니다.
`vmm.h` 의 플래그 → `vmm.c` 의 인덱스 매크로 → `vmm_map_page` → `idt.c` 의 페이지 폴트 처리 순서로 읽으세요.

## 가상 주소를 네 조각으로 나누기

Step 01-3에서는 2MB 대형 페이지로 PT 단계를 건너뛰었지만, 4KB 단위로 세밀하게 매핑하려면 네 단계를 모두 거쳐야 합니다.
x86-64의 가상 주소는 64비트 중 하위 48비트만 의미가 있고, 이 48비트가 다섯 부분으로 나뉩니다.

```
비트  47..39   38..30   29..21   20..12   11..0
     PML4 인덱스 PDPT 인덱스 PD 인덱스  PT 인덱스  페이지 안 오프셋
```

인덱스 하나가 9비트라 0~511, 즉 테이블 한 장의 512칸 중 하나를 고릅니다. 테이블 한 장은 8바이트 × 512칸 = 4KB로, 딱 프레임 하나 크기입니다.
CPU의 변환 과정은 이렇습니다. CR3가 가리키는 PML4에서 PML4 인덱스 칸을 읽으면 PDPT의 물리 주소가 나옵니다. 그 PDPT에서 PDPT 인덱스 칸을 읽으면 PD의 주소가, PD에서 PD 인덱스 칸을 읽으면 PT의 주소가, PT에서 PT 인덱스 칸을 읽으면 마침내 4KB 프레임의 주소가 나옵니다. 여기에 오프셋 12비트를 더한 것이 최종 물리 주소입니다.

`vmm.c` 는 이 분해를 매크로로 표현합니다.

```c
#define PML4_IDX(v) (((v) >> 39) & 0x1FF)
#define PDPT_IDX(v) (((v) >> 30) & 0x1FF)
#define PD_IDX(v)   (((v) >> 21) & 0x1FF)
#define PT_IDX(v)   (((v) >> 12) & 0x1FF)
#define ENTRY_ADDR(e) ((e) & ~0xFFFUL)
```

엔트리는 "다음 테이블(또는 프레임)의 물리 주소 | 하위 12비트 플래그" 모양입니다. 테이블과 프레임은 모두 4KB 정렬이라 주소의 하위 12비트가 항상 0이므로, 그 자리를 플래그로 씁니다. `ENTRY_ADDR` 는 플래그를 지우고 주소만 꺼냅니다.
플래그는 `vmm.h` 에 세 개가 정의되어 있습니다. bit 0 `VMM_PRESENT`(존재함), bit 1 `VMM_WRITABLE`(쓰기 가능), bit 2 `VMM_USER`(ring 3도 접근 가능)입니다. `VMM_USER` 는 아직 쓰지 않지만 Step 12에서 주인공이 됩니다.

## vmm_map_page: 없으면 만들고, 있으면 따라간다

매핑 하나를 추가하는 것은 결국 PT의 한 칸에 프레임 주소를 쓰는 일입니다. 문제는 그 PT가, 또는 그 위의 PD나 PDPT가 아직 없을 수 있다는 점입니다.
그래서 `vmm_map_page` 는 위에서부터 한 단계씩 내려가며 같은 일을 반복합니다. 이번 단계의 엔트리가 Present가 아니면 PMM에서 프레임을 하나 받아 0으로 채우고, 그 주소를 엔트리에 연결합니다. Present라면 엔트리의 주소를 따라 다음 테이블로 내려갑니다.

```c
if (!(pml4[pml4i] & VMM_PRESENT)) {
    uint64_t *pdpt = pmm_alloc_page();
    clear_page(pdpt);
    pml4[pml4i] = (uint64_t)pdpt | VMM_PRESENT | VMM_WRITABLE;
}
uint64_t *pdpt = (uint64_t *)ENTRY_ADDR(pml4[pml4i]);
```

여기서 Step 05의 약속이 빛을 발합니다. `pmm_alloc_page()` 가 준 것은 물리 주소인데, 1GB 아래는 아이덴티티 매핑이라 그 값을 그대로 포인터로 써서 `clear_page` 로 0을 채울 수 있습니다. 엔트리에서 꺼낸 다음 테이블의 물리 주소도 마찬가지로 바로 포인터로 씁니다. 아이덴티티 매핑이 없었다면, 페이지 테이블을 고치기 위해 먼저 페이지 테이블을 고쳐야 하는 닭과 달걀 문제에 빠졌을 것입니다.
새 테이블을 **반드시 0으로 채우는** 것도 중요합니다. PMM이 준 프레임에는 이전에 쓰던 쓰레기 값이 남아 있을 수 있고, 그중 bit 0이 1인 칸이 있으면 CPU는 그걸 유효한 매핑으로 믿고 엉뚱한 메모리에 접근합니다.

PD 단계에서는 한 가지를 더 확인합니다. 그 PD 엔트리에 PS 비트(bit 7)가 켜져 있으면, 그 자리는 이미 2MB 대형 페이지가 차지하고 있고 아래에 PT가 없습니다. 거기에 4KB 매핑을 끼워 넣을 수는 없으므로 오류를 출력하고 거절합니다.
0~1GB는 Step 01-3이 전부 2MB 페이지로 덮었으니, 이 함수로 매핑할 수 있는 주소는 1GB 위뿐입니다. 이것이 이후 단계의 주소 배치를 정합니다. 힙은 12GB(`0x300000000`), 유저 코드는 16GB(`0x400000000`), 유저 스택은 20GB(`0x500000000`)에 자리를 잡게 됩니다.

마지막으로 PT 칸에 `phys | flags | VMM_PRESENT` 를 쓰고 `invlpg` 를 실행합니다.

## TLB: CPU의 주소 변환 캐시

CPU는 메모리에 접근할 때마다 네 단계를 따라가지 않습니다. 그러면 메모리 접근 한 번에 네 번의 추가 접근이 필요해 너무 느리기 때문에, 최근에 변환한 결과를 **TLB(Translation Lookaside Buffer)** 라는 캐시에 보관합니다.
문제는 페이지 테이블을 바꿔도 TLB는 자동으로 갱신되지 않는다는 점입니다. 매핑을 바꾼 뒤 TLB에 옛 결과가 남아 있으면 CPU는 옛 프레임에 접근합니다. 그래서 매핑을 바꿀 때마다 `invlpg 주소` 로 그 주소의 TLB 항목을 지웁니다.
`vmm_unmap_page` 도 같은 경로로 PT 칸을 찾아 0으로 만들고 `invlpg` 합니다. 중간 테이블은 비어도 지우지 않고 그대로 둡니다.
나중에 많은 페이지를 한꺼번에 해제할 때(Step 21의 exec)는 하나씩 `invlpg` 하는 대신 CR3를 다시 써서 TLB 전체를 비우는 방법을 씁니다.

`vmm_get_pml4()` 는 CR3를 읽어 현재 PML4의 주소를 돌려줍니다. 지금은 boot.s가 만든 PML4 하나를 커널 전체가 공유하므로, 모든 매핑은 이 PML4에 덧붙여집니다. 함수가 `pml4` 를 인자로 받게 만들어 둔 것은, Step 20에서 프로세스마다 다른 PML4를 갖게 될 때를 위한 준비입니다.

## 페이지 폴트 진단

매핑이 없는 주소에 접근하거나, 읽기 전용 페이지에 쓰거나, 커널 페이지에 유저가 접근하면 CPU는 14번 예외, **페이지 폴트(#PF)** 를 일으킵니다. 이때 CPU는 두 가지 단서를 남깁니다. CR2 레지스터에는 접근하려던 가상 주소가, 에러 코드에는 원인이 담깁니다.
`exception_handler` 는 14번일 때 이 둘을 풀어서 출력한 뒤 패닉합니다.

```c
printf("[vmm] Page Fault: addr=%p  err=0x%lx (%s %s %s)\n", (void *)cr2, r->err_code,
       (r->err_code & 1) ? "protection" : "not-present",
       (r->err_code & 2) ? "write"      : "read",
       (r->err_code & 4) ? "user"       : "kernel");
```

에러 코드의 bit 0은 "매핑은 있는데 권한 위반"(1)인지 "매핑 자체가 없음"(0)인지를, bit 1은 쓰기였는지 읽기였는지를, bit 2는 ring 3에서 일어났는지 ring 0에서 일어났는지를 알려 줍니다.
이 세 단어 조합만 봐도 원인을 상당히 좁힐 수 있습니다. 예를 들어 `not-present write kernel` 이면 커널이 매핑하지 않은 곳에 쓴 것이고, `protection read user` 면 유저 코드가 커널 전용 페이지를 읽으려 한 것입니다. Step 14에서 유저 모드 진입을 처음 시도할 때 바로 이 메시지가 문제를 알려 줍니다.

## 이 단계가 뒤에 남기는 것

`vmm_map_page` 는 커널에서 가장 많이 불리는 함수 중 하나가 됩니다. 힙(07), 유저 코드와 스택(12·14), ELF 세그먼트(18)가 모두 이 함수로 매핑됩니다.
"1GB 아래는 고정, 1GB 위는 자유롭게 매핑"이라는 주소 공간의 큰 그림도 여기서 확정됩니다. `VMM_PRESENT`/`VMM_WRITABLE`/`VMM_USER` 플래그는 이후 모든 매핑의 언어가 되고, 특히 `VMM_USER` 는 Step 20의 fork와 Step 21의 exec가 "유저 페이지"를 구분하는 표시로 쓰입니다.
페이지 폴트 메시지의 세 단어는 이후 디버깅 내내 가장 먼저 보게 될 단서입니다.

## 직접 만들어 보기

인덱스 매크로와 `vmm_get_pml4()` 를 먼저 만들고, 이미 매핑되어 있는 주소(예: 커널 코드가 있는 `0x100000`)를 손으로 따라가 보세요. PML4[0] → PDPT[0] → PD[0]까지 내려가면 PS 비트가 켜진 엔트리가 나오고, 그 엔트리의 주소가 0이라는 것을 확인할 수 있습니다.
다음으로 `vmm_map_page` 를 "없으면 만들고, 있으면 따라간다"는 규칙대로 작성하고, 16GB 주소에 매핑해 값을 쓰고 읽습니다.
`invlpg` 를 일부러 빼고, 같은 가상 주소를 다른 프레임으로 다시 매핑해서 옛 값이 읽히는지 시험해 보는 것도 좋습니다. QEMU에서는 재현되지 않을 수도 있지만, 재현되면 TLB의 존재를 확실히 느낄 수 있습니다.
마지막으로 `vmm_unmap_page` 후에 접근해 페이지 폴트 메시지를 확인합니다.

## 확인하기

부팅 로그에 다음 줄들이 나옵니다.

```
[vmm] kernel PML4 at 0x00000000001.....
[test] virt=0x0000000400000000 -> phys=0x0000000000xxx000  value=0xc0ffee
```

`main.c` 의 `/* vmm_unmap_page(pml4, virt); printf("%lx\n", *v); */` 주석을 풀면, 매핑을 해제한 뒤 읽으려다 다음 메시지와 함께 패닉합니다.

```
[vmm] Page Fault: addr=0x0000000400000000  err=0x0 (not-present read kernel)
```

## 막혔을 때

매핑했는데 접근하자마자 페이지 폴트가 난다면, 마지막 PT 칸에 `VMM_PRESENT` 를 넣지 않았거나 `invlpg` 를 빠뜨린 것입니다. 메시지의 주소와 원인을 먼저 보세요.
`2MB large page exists` 오류가 나면 1GB 아래 주소에 매핑하려 한 것입니다.
매핑 후 엉뚱한 메모리가 덮어써지거나 무관한 곳에서 페이지 폴트가 난다면, 새 테이블을 0으로 채우지 않아 쓰레기 엔트리가 Present로 보이는 경우가 많습니다.
인덱스 매크로의 시프트 값(39, 30, 21, 12) 중 하나를 틀리면 엉뚱한 칸에 매핑되어 "매핑했는데 안 보이는" 증상이 납니다.
