# Step 01-3 — 64비트 롱 모드 진입과 첫 C 함수

지금 CPU는 GRUB이 내려놓은 그대로 32비트 보호 모드에 있고, 페이징은 꺼져 있습니다. 이번 단계에서는 이 CPU를 64비트 **롱 모드** 로 바꾸고, 64비트로 컴파일된 C 함수 `kernel_main` 을 부릅니다.
`boot.s` 에 100줄 가까이 추가되는 이 단계가 Step 01에서 가장 어렵습니다. 순서 하나, 비트 하나만 틀려도 CPU는 아무 메시지 없이 리셋되고 GRUB 화면으로 돌아갑니다(트리플 폴트).
그래서 앞 단계의 `OK` 를 일부러 남겨 두었습니다. 이번 단계를 마치면 화면에 두 줄이 보여야 합니다. 첫 줄의 `OK` 는 32비트 코드가, 둘째 줄의 `Hello from 64-bit C!` 는 64비트 C 코드가 찍은 것입니다.
`OK` 만 보이고 둘째 줄이 없다면, 문제는 "32비트 → 64비트 전환" 구간 어딘가에 있다는 뜻이 됩니다.

바뀌는 파일은 `boot/boot.s` 와 새로 생기는 `kernel/main.c` 입니다. `boot.s` 는 위에서부터 데이터(GDT) → BSS(페이지 테이블) → 32비트 코드 → 64비트 코드 순서로 읽으면 됩니다.

## 왜 롱 모드에는 페이징이 필수인가

x86-64 CPU는 64비트 모드로 들어가는 조건으로 **페이징을 켤 것** 을 요구합니다. 32비트 시절에는 페이징이 선택 사항이었지만, 롱 모드는 4단계 페이지 테이블을 통한 주소 변환을 전제로 설계됐기 때문입니다.
그래서 64비트 코드를 한 줄이라도 실행하려면, 그 전에 어셈블리로 페이지 테이블을 만들어 두어야 합니다. C 코드는 64비트로 컴파일됐으니 아직 부를 수 없습니다.

가상 주소를 물리 주소로 바꾸는 방법을 정하는 것이 페이지 테이블입니다. 여기서는 가장 단순한 방식을 씁니다. **가상 주소 0~1GB를 물리 주소 0~1GB에 그대로 대응** 시키는 것으로, 이를 아이덴티티 매핑이라고 합니다.
이렇게 하면 페이징을 켜기 전과 후에 모든 주소가 같은 의미를 가집니다. 지금 실행 중인 코드의 주소, 스택 주소, VGA 버퍼 `0xB8000` 이 페이징을 켜는 순간에도 그대로 유효해야 하니, 다른 선택지가 사실상 없습니다.

## 페이지 테이블 세 장으로 1GB 매핑하기

x86-64의 정식 변환은 PML4 → PDPT → PD → PT 네 단계를 거쳐 4KB 페이지에 도달합니다. 각 테이블은 8바이트 엔트리 512개, 정확히 4KB입니다.
그런데 PD 엔트리에 PS(Page Size) 비트를 켜면 PT 단계를 건너뛰고 그 엔트리 하나가 **2MB 대형 페이지** 를 직접 가리킵니다. 512칸 × 2MB = 1GB이니, PD 한 장을 꽉 채우면 1GB가 한 번에 매핑됩니다.
그래서 필요한 테이블은 PML4, PDPT, PD 세 장뿐입니다.

```asm
.section .bss
.align 4096
pml4: .skip 4096
pdpt: .skip 4096
pd:   .skip 4096
```

`.align 4096` 이 중요합니다. 엔트리에 담기는 다음 테이블의 주소는 하위 12비트를 플래그로 쓰기 때문에, 테이블은 반드시 4KB 경계에 있어야 합니다. BSS에 두었으니 GRUB이 0으로 채워 주고, 0인 엔트리는 "없음(Present=0)"을 뜻합니다.

이제 테이블을 연결합니다.

```asm
    mov $pdpt, %eax
    or  $0x3, %eax          /* Present | Writable */
    mov %eax, pml4          /* PML4[0] → PDPT */

    mov $pd, %eax
    or  $0x3, %eax
    mov %eax, pdpt          /* PDPT[0] → PD */
```

PML4의 0번 칸이 PDPT를, PDPT의 0번 칸이 PD를 가리키게 합니다. 0번 칸만 채우는 이유는 0~1GB 주소가 전부 각 테이블의 0번 인덱스에 해당하기 때문입니다.
`0x3` 은 Present(bit 0)와 Writable(bit 1)입니다. 엔트리는 64비트지만, 지금 주소는 4GB 아래라 상위 32비트가 0이고 BSS가 0으로 채워져 있으니 하위 32비트만 쓰면 됩니다.

PD 512칸은 루프로 채웁니다.

```asm
    mov $pd, %edi
    mov $0x83, %eax         /* addr=0 | Present | Writable | PS(2MB) */
    xor %edx, %edx
    mov $512, %ecx
.fill_pd:
    mov %eax, (%edi)        /* 하위 32비트 */
    mov %edx, 4(%edi)       /* 상위 32비트 = 0 */
    add $8, %edi
    add $0x200000, %eax     /* 다음 2MB */
    loop .fill_pd
```

`0x83` 은 Present, Writable, 그리고 bit 7인 PS입니다. 첫 칸은 물리 0번지부터 2MB, 다음 칸은 2MB부터 2MB, 이런 식으로 512번 반복합니다. `loop` 는 `ecx` 를 하나 줄이고 0이 아니면 점프하는 명령입니다.

이 1GB 아이덴티티 매핑은 이번 단계만을 위한 임시 장치가 아닙니다. 커널은 끝까지 이 매핑 위에서 돕니다.
Step 05의 물리 메모리 관리자는 "물리 주소를 그대로 포인터로 써도 된다"는 이 성질을 이용하고, Step 06의 가상 메모리 관리자는 새 페이지 테이블을 만들 때 그 물리 주소에 바로 값을 씁니다. QEMU를 512MB로 띄우는 이유도 모든 RAM이 이 1GB 안에 들어오게 하려는 것입니다.
대신 1GB 아래는 전부 2MB 대형 페이지로 덮여 있어서, 나중에 4KB 단위로 세밀하게 매핑하고 싶은 영역(힙, 유저 프로그램)은 1GB 위의 주소를 쓰게 됩니다.

## 롱 모드로 가는 네 단계

페이지 테이블이 준비됐으면 CPU 설정을 정해진 순서대로 바꿉니다.

```asm
    mov %cr4, %eax
    or  $0x20, %eax         /* CR4.PAE (bit 5) */
    mov %eax, %cr4

    mov $pml4, %eax
    mov %eax, %cr3          /* 페이지 테이블 최상위 주소 */

    mov $0xC0000080, %ecx   /* EFER MSR */
    rdmsr
    or  $0x100, %eax        /* EFER.LME (bit 8) */
    wrmsr

    mov %cr0, %eax
    or  $0x80000000, %eax   /* CR0.PG (bit 31) */
    mov %eax, %cr0
```

먼저 CR4의 PAE 비트를 켭니다. PAE는 64비트 엔트리를 쓰는 페이지 테이블 형식인데, 롱 모드의 4단계 테이블이 이 형식을 확장한 것이라 먼저 켜야 합니다.
다음으로 CR3에 PML4의 주소를 넣습니다. CR3는 "현재 쓰는 페이지 테이블이 어디 있는가"를 담는 레지스터이고, 나중에 프로세스마다 다른 주소 공간을 쓸 때(Step 22) 프로세스를 바꿀 때마다 이 값을 갈아 끼우게 됩니다.
세 번째로 EFER라는 모델 특정 레지스터(MSR)의 LME 비트를 켭니다. MSR은 일반 `mov` 로 다룰 수 없고, `ecx` 에 번호를 넣고 `rdmsr` 로 `edx:eax` 에 읽어 온 뒤 `wrmsr` 로 다시 씁니다. LME는 "페이징을 켜면 롱 모드로 가겠다"는 예약입니다.
마지막으로 CR0의 PG 비트를 켜서 페이징을 시작합니다. LME가 켜진 상태에서 페이징이 켜지는 순간 CPU는 롱 모드에 들어갑니다.

그런데 이 순간의 CPU는 아직 완전한 64비트가 아닙니다. 롱 모드 안에는 기존 32비트 코드를 그대로 돌리는 **호환 모드** 와 진짜 **64비트 모드** 가 있고, 둘 중 어느 쪽인지는 현재 코드 세그먼트(CS)가 가리키는 디스크립터의 L 비트로 정해집니다.
지금 CS는 GRUB이 만든 32비트 세그먼트라서 호환 모드입니다. 64비트로 가려면 L 비트가 켜진 코드 세그먼트로 CS를 바꿔야 하고, 그러려면 GDT가 필요합니다.

## 64비트 GDT

GDT(Global Descriptor Table)는 세그먼트 디스크립터의 표입니다. 64비트에서는 세그먼트의 base와 limit이 거의 무시되기 때문에 GDT의 역할은 크게 줄었지만, **권한 수준과 64비트 여부** 는 여전히 여기서 정합니다.

```asm
gdt64:
    .quad 0x0000000000000000    /* 0x00: null */
    .quad 0x00AF9A000000FFFF    /* 0x08: 커널 코드 (L=1, P=1, DPL=0) */
    .quad 0x00CF92000000FFFF    /* 0x10: 커널 데이터 (P=1, DPL=0, RW=1) */
gdt64_end:

gdt64_ptr:
    .word gdt64_end - gdt64 - 1
    .quad gdt64
```

첫 칸은 규격상 반드시 비워 둬야 하는 null 디스크립터입니다. 둘째 칸이 코드 세그먼트로, 접근 바이트 `0x9A` 는 "존재함, 권한 0, 실행·읽기 가능한 코드"이고, 플래그 니블 `0xA` 의 bit 1이 바로 L(64비트) 비트입니다. 셋째 칸은 데이터 세그먼트로 접근 바이트 `0x92`("존재함, 권한 0, 읽기·쓰기 가능한 데이터")입니다.
각 디스크립터는 GDT 안에서 8바이트씩 떨어져 있으므로, 이 디스크립터들을 고르는 값(셀렉터)은 각각 `0x08` 과 `0x10` 이 됩니다.
`gdt64_ptr` 는 `lgdt` 명령이 읽는 10바이트 구조로, 앞 2바이트는 표의 크기에서 1을 뺀 값, 뒤 8바이트는 표의 주소입니다. 크기를 `gdt64_end - gdt64 - 1` 로 계산해 두었기 때문에, Step 10에서 유저 세그먼트를 덧붙여도 이 줄은 고칠 필요가 없습니다.

`0x08` 이 커널 코드, `0x10` 이 커널 데이터라는 약속은 이후 계속 쓰입니다. Step 02의 IDT 게이트는 핸들러가 실행될 코드 세그먼트로 `0x08` 을 적고, Step 10은 이 표 뒤에 유저 세그먼트와 TSS를 이어 붙입니다.

## far jump로 64비트 코드에 들어가기

```asm
    lgdt gdt64_ptr
    ljmpl $0x08, $start64

.code64
start64:
    mov $0x10, %ax
    mov %ax, %ds
    mov %ax, %es
    mov %ax, %fs
    mov %ax, %gs
    mov %ax, %ss
```

`lgdt` 로 새 GDT를 등록한 뒤, `ljmpl $0x08, $start64` 로 **세그먼트까지 바꾸는 점프** 를 합니다. 일반 `jmp` 는 주소만 바꾸지만 far jump는 CS도 함께 바꿉니다. CS가 L=1인 `0x08` 로 바뀌는 순간 CPU는 64비트 모드로 명령을 해석하기 시작합니다.
그래서 점프 대상인 `start64` 는 `.code64` 아래에 있어야 합니다. 같은 바이트라도 32비트와 64비트에서 다른 명령으로 해석되기 때문입니다.
64비트에 도착하면 나머지 세그먼트 레지스터를 데이터 세그먼트 `0x10` 으로 맞춥니다. 64비트에서는 이 값들이 주소 계산에 거의 쓰이지 않지만, GRUB 시절의 옛 값이 남아 있으면 나중에 인터럽트에서 돌아올 때(`iretq`) 문제를 일으킬 수 있습니다.

## kernel_main 부르기

```asm
    lea stack_top(%rip), %rsp
    xor %rbp, %rbp

    movl mb_magic(%rip), %edi
    movl mb_info(%rip), %esi

    call kernel_main
```

스택 포인터를 64비트 레지스터 `rsp` 로 다시 맞춘 뒤, 앞 단계에서 저장해 둔 두 값을 꺼냅니다. System V AMD64 호출 규약에서 첫 번째 인자는 `rdi`, 두 번째는 `rsi` 로 전달됩니다. 32비트 레지스터 `edi`, `esi` 에 값을 넣으면 상위 32비트는 자동으로 0이 됩니다.
`(%rip)` 가 붙은 주소 지정은 "현재 명령 위치 기준 상대 주소"라는 뜻으로, 64비트 코드에서 전역 변수를 가리킬 때 흔히 쓰는 방식입니다.
`call` 이 돌아오는 일은 없어야 하지만, 혹시 돌아오면 `cli; hlt` 루프로 멈추게 해 둡니다.

`kernel/main.c` 의 첫 버전은 출력 드라이버 없이 VGA 메모리에 직접 씁니다.

```c
void kernel_main(uint64_t magic, uint64_t info) {
    volatile uint16_t *vga = (uint16_t *)0xB8000 + 80;   /* 두 번째 줄 */
    const char *msg = (magic == MB2_BOOT_MAGIC) ? "Hello from 64-bit C! (magic OK)"
                                                : "Hello from 64-bit C! (bad magic)";
    for (int i = 0; msg[i]; i++)
        vga[i] = (0x0F << 8) | msg[i];
    for (;;) __asm__ volatile("hlt");
}
```

`uint16_t` 포인터에 80을 더하면 160바이트, 즉 한 줄 뒤입니다. 첫 줄의 `OK` 를 지우지 않으려고 둘째 줄에 씁니다.
매직 값을 확인하는 것은 단순한 장식이 아닙니다. 이 메시지가 `magic OK` 로 나온다면 32비트에서 저장한 값이 64비트까지 무사히 왔고, `rdi` 로 인자를 넘기는 호출 규약도 맞았다는 뜻입니다.
`volatile` 은 컴파일러가 "아무도 읽지 않는 메모리에 쓰는 코드"라고 판단해 지워 버리지 않게 합니다.

## 이 단계가 뒤에 남기는 것

이번 단계에서 깔린 약속이 가장 많습니다. 0~1GB는 끝까지 아이덴티티 매핑이고, 1GB 위는 나중에 자유롭게 쓸 수 있는 빈 공간입니다. CR3는 boot.s가 만든 PML4를 가리키고, Step 06의 `vmm_get_pml4()` 가 이 값을 읽어 그 위에 매핑을 덧붙입니다.
GDT의 `0x08`/`0x10` 셀렉터는 모든 커널 코드의 기준이 됩니다. 그리고 `kernel_main(magic, info)` 는 이제부터 커널 초기화가 한 줄씩 쌓이는 자리입니다. Step 23에 이르면 이 함수에 스무 개 가까운 초기화 호출이 순서대로 들어서게 됩니다.

## 직접 만들어 보기

이 단계는 한 번에 다 쓰지 말고, 앞에서부터 하나씩 넣으며 매번 부팅해 보는 게 좋습니다.
먼저 페이지 테이블을 채우는 코드만 넣고 부팅해서 `OK` 가 여전히 나오는지 봅니다. 페이징을 켜기 전이니 아무 영향이 없어야 합니다.
다음으로 PAE, CR3, EFER까지 넣고 다시 확인합니다. 이것도 아직 페이징을 켜지 않았으니 `OK` 가 나와야 합니다.
CR0.PG를 켜는 줄을 넣고 바로 뒤에 `hlt` 를 두어 보세요. 이 시점에서 리셋이 일어난다면 페이지 테이블이 틀린 것입니다. 지금 실행 중인 코드의 주소가 매핑되어 있지 않으면 다음 명령을 가져오는 순간 페이지 폴트가 나고, 그걸 처리할 IDT도 없으니 트리플 폴트로 이어집니다.
마지막으로 GDT와 far jump, `start64` 를 넣고, 처음에는 `start64` 에서 `hlt` 만 한 뒤 QEMU 모니터의 `info registers` 로 `CS=0008` 과 64비트 레지스터(`RIP=00000000001000xx`)가 보이는지 확인합니다. 그다음에 C 함수를 부릅니다.

## 확인하기

화면 첫 줄에 초록색 `OK`, 둘째 줄에 흰 글씨로 `Hello from 64-bit C! (magic OK)` 가 보이면 성공입니다.
`(bad magic)` 이 나온다면 64비트 전환은 성공했지만, 값을 저장하는 순서나 `edi`/`esi` 로 넘기는 부분이 틀린 것입니다.

## 막혔을 때

계속 GRUB으로 돌아가며 재부팅된다면 트리플 폴트입니다. QEMU를 `-d int,cpu_reset -no-reboot` 옵션으로 띄우면 리셋 직전에 어떤 예외가 났는지와 레지스터 상태가 터미널에 찍힙니다. `v=0e`(페이지 폴트)라면 페이지 테이블을, `v=0d`(일반 보호 예외)라면 GDT 디스크립터나 far jump를 의심하세요.
`OK` 는 보이는데 둘째 줄이 없다면, 리셋 없이 멈춰 있는지부터 확인하세요. 멈춰 있다면 `kernel_main` 에 도착하기 전 어딘가에서 `hlt` 에 걸렸을 수 있습니다.
링크 단계에서 `relocation truncated to fit` 이 나오면 C 코드가 PIC로 컴파일된 경우가 많으니 `-fno-pic` 가 들어갔는지 확인하세요.
PD 루프의 `add $0x200000` 에서 0을 하나 빠뜨리는 실수도 흔합니다. 2MB 대형 페이지의 주소는 반드시 2MB 경계여야 해서, 어긋난 주소가 들어간 엔트리는 예약 비트 위반으로 페이지 폴트를 일으킵니다.
